# Дорожная карта

Что мы собираемся сделать в go-bpm и в каком порядке. План составлен по отзывам на
[презентацию](/go-bpm.pdf) с позиций технического директора банка и solution-архитектора команды: что мешает взять
go-bpm в работу и что спросят на архитектурном комитете.

Порядок — от простого к сложному: сначала то, что снимает вопросы малой ценой, потом недостающие элементы BPMN.
Это план, а не обещание сроков. Что уже работает сегодня — в [документации](/docs/); что не поддерживается —
в [Моделировании BPMN](/docs/bpmn/#что-не-поддерживается). Предложения и приоритеты обсуждаем
в [issues на GitHub](https://github.com/nicolas-vp/go-bpm/issues).

| Трудоёмкость | Что значит |
|---|---|
| **Легко** | дни: документация или небольшая доработка без изменения модели исполнения |
| **Средне** | одна-три недели: новый элемент или подсистема поверх существующих механизмов движка |
| **Сложно** | месяц и больше: меняется модель исполнения токенов |

## 1. Документация — легко

Ответы на вопросы, которые архитектор задаёт первыми. Код движка не меняется.

| Что | Зачем |
|---|---|
| **Семантика исполнения** | одна страница: доставка «как минимум один раз», аренда задач, что повторяется при сбое, почему методы и обработчики должны быть идемпотентными, что выносить в service task |
| **Ожидание внешних событий сегодня** | пока нет сообщений: задача пользователя как точка ожидания, которую закрывает система через API, и опрос из service task — с примерами и подводными камнями |
| **Безопасность** | как закрыть API и консоль своим middleware, откуда брать пользователя задач, что не класть в переменные процесса (персональные данные) |
| **Изменение процессов** | что можно менять при живых экземплярах, как удалять элементы, как запустить несовместимую версию рядом со старой на `KindPrefix` |
| **Переход с Camunda 7** | что переносится (схемы, таблицы DMN), что переписывается (Java-делегаты, выражения), как жить с экземплярами в пути |
| **Референсная архитектура** | сервис с go-bpm в Kubernetes: с отдельной базой движка и с общей базой сервиса, плюсы и минусы обоих вариантов |

## 2. Эксплуатация и безопасность — легко

Небольшие доработки движка, после которых go-bpm можно выводить в продакшен без самописной обвязки.

| Что | Зачем |
|---|---|
| **Метрики Prometheus** | `/metrics` без новых зависимостей: глубина очереди по видам, упавшие задачи, возраст самой старой задачи, экземпляры по статусам. Сейчас то же самое — SQL-запросами из документации |
| **Хуки движка** | вызовы на начало и конец шага, задачи, повтор и падение — точка подключения OpenTelemetry и своих метрик без зависимости go-bpm от OpenTelemetry |
| **Авторизация API и консоли** | опция с функцией, которая по запросу возвращает пользователя и его группы; API задач пользователей берёт исполнителя из неё, а не из тела запроса |
| **Журнал операций** | кто и когда повторил упавшую задачу, исправил переменные, отменил экземпляр — в таблице и в истории экземпляра |
| **Очистка истории** | настройка срока хранения завершённых экземпляров вместе с историей, правилами DMN и задачами пользователей. Сейчас они не удаляются, очистку пишет каждая команда сама |
| **Безопасность поставки** | `govulncheck` в CI, SBOM и подписанные релизы и образы |

## 3. BPMN, которого не хватает чаще всего — средне

Новые элементы поверх механизмов, которые в движке уже есть: точек ожидания, задач очереди и гонки задачи
с граничным таймером.

| Что | Зачем |
|---|---|
| **Сообщения с корреляцией по бизнес-ключу** | промежуточное событие и receive task ждут сообщение; его отправляют через `POST /api/v1/messages` или из Go. Главный пробел для процессов, которые ждут callback внешней системы: платёж, ответ бюро, решение антифрода |
| **Граничный таймер у задачи пользователя и call activity** | эскалация по сроку: задачу не взяли за день — уходим другой веткой |
| **Непрерывающий граничный таймер** | напоминание или уведомление без прерывания задачи |
| **Таймеры `timeDate` и `timeCycle`** | «в 9:00 следующего рабочего дня», «каждый час» |
| **Секционирование истории** | `bpm_history` по времени: очистка удалением секций и предсказуемый рост таблиц |
| **Нагрузочный тест на серверном железе** | несколько экземпляров сервиса на одной базе, задержки p99, переключение PostgreSQL на реплику — в дополнение к [тесту по методике 2021 года](/docs/performance/) |

## 4. Сложные элементы BPMN — сложно

Здесь меняется модель исполнения: движок начинает считать токены и откатывать уже выполненные шаги.

| Что | Зачем |
|---|---|
| **Multi-instance** | параллельный и последовательный: «согласовать у всех из списка», «запросить все банки и дождаться ответов» |
| **Компенсации** | откат саги средствами BPMN: компенсирующие задачи вместо ручных веток отката |
| **Inclusive и event-based gateway** | несколько веток по условиям; ожидание первого из событий — сообщения или таймера |
| **Старт по сообщению и граничное событие сообщения** | процесс стартует по входящему событию; сообщение прерывает задачу |
| **Атрибуты Camunda 7 в генераторе** | перенос схем Camunda 7 (`camunda:*`) без перерисовки в моделере Camunda 8 |

## Чего не будет

Это не пробелы, а решения, на которых построен go-bpm.

- **Деплоя BPMN без релиза сервиса.** Процесс — исходник: он проверяется компилятором, тестами и ревью и
  выкатывается вместе с кодом, который его исполняет.
- **Других СУБД.** Очередь, транзакции шагов и блокировки построены на PostgreSQL.
- **Других языков.** go-bpm — библиотека для Go-сервисов; процессы других сервисов вызываются из service task.
